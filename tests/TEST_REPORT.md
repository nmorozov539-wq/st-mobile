## 0.7.15 — Second phone test, preset import, several personas, DeepSeek

Every 0.7.14 phone-test failure that can be reproduced off the phone was reproduced against a fresh ST 1.19.0 mock fixture before it was fixed.

- **Root causes found while testing:** a long-run stall ("ST is still busy after submission") came from character cards whose advanced fields had been saved as two-item lists. The engine frame was opened as `/?mobileRuntime=1`; with ST's `<base href="/">`, any query string makes jQuery UI load the whole ST page into the Backgrounds tab, so `#form_create` existed twice and every ST character save posted those fields twice. `Generate` then stopped inside `getCharacterCardFields()` without sending a request. The frame is now marked by its name, and `card-repair.js` repairs damaged cards once (verified on a damaged card from the fixture: all fields restored in both `chara` and `ccv3`, and replies go through again). Separately, focus could land inside the hidden engine frame, so Escape (and Android Back) went to ST instead of Pocket's close watcher; the frame is now `inert` with a blur guard.
- **New suite `tests/phone-fixes-2-ui.cjs`, 26 checks:** Back walks Memory → chat → Chats → Home with no history entries, reconnect adds none, token counts on older replies, regenerate hides then restores the old reply, no alternative notice, Summarize reports its outcome, preset import (listed, does not switch, numbered copy, can be chosen), several personas (adds instead of replacing, character lists all, new chat asks, chat's own persona shown, each link removable), DeepSeek (key-only form, Connect loads models, ST uses its DeepSeek source, a reply goes through the chosen model via a reverse proxy to the mock, switching back restores the custom endpoint), no page errors.
- **232 unit tests pass** (new `card-repair.test.js`; the preset-import collision test now expects a numbered copy instead of a refusal).
- **Browser regressions pass:** phone-fixes 13, Home 10, Settings 21, World Info UI 18, World Info bridge 22, Memory 40, chat 65, preset 42, preset scope 3, preset layout 2, new chat 35, Character 34, card actions 29, character associations 18, association actions 37, association loading 4, library races 14, repair kit. `chat-ui`, `preset-ui` and `new-chat-ui` ran this time with a Moss card imported through ST. ## 0.7.14 — Fixes from the first phone test

Every critical and major item in the 0.7.13 phone test was reproduced against a fresh ST 1.19.0 mock fixture before it was fixed, except the Android-only ones (the Chrome history intervention behind Back, and the browser freezing a backgrounded tab), which were simulated.

- **Root causes:** the Memory page kept the `memory-page` class on `#page-content`, so its 2-second poll repainted over any page; Memory actions ran on whichever chat the engine last had open; Android Back mapped every page to Home, and Chrome skips history entries pushed without a user gesture, so repeated Back left the app; `characterId===index` compared ST's string id with a number, so a fresh chat for the open character reused the old chat array; persona save nulled its draft before the refresh redrew the editor; the "This chat" persona link existed only in an unused frontend copy of the bridge.
- **New suite `tests/phone-fixes-ui.cjs`, 13 checks:** fresh chat for the open character holds only its greeting; Memory names the chat on screen and never paints over World Info; Back asks before discarding an entry, Cancel keeps the typing, and Back from Entry, Activation and tab pages lands on the right page; a persona with a portrait saves; a card's embedded lorebook imports and links as primary; the engine reconnects without pressing Reconnect.
- **228 unit tests pass** (the unused `frontend/workspace.js` copy was removed). Home 10, Settings 21, World Info UI 18, Memory page 40 and Character 34 browser checks pass. `libraries-ui`, `preset-ui` and `new-chat-ui` need the seeded Moss fixture and were not run; `character-associations-ui` stops at the same multi-persona sheet step on 0.7.13, so that is a fixture difference rather than a 0.7.14 change.

## 0.7.13 — Review pass before phone testing

Re-read all 0.7.10–0.7.12 code against the ST 1.19.0 source. Twelve issues found and fixed; two got dedicated regression checks, and a third was caught by an intermittent failure in the World Info UI suite.

- **Fixed, would have shown up on the phone:** the Activation sliders re-rendered on every input event, so a finger drag was cancelled the moment it moved (Min activations / Max recursion steps); the Settings endpoint field re-rendered on blur, so tapping from it into the API key field lost the tap and the keyboard.
- **Fixed, found by a flaky suite:** every page paints into the same `#page-content` node, so a slow reload (for example the library refreshing after an activation save) could repaint over whichever page the person had moved to. Each panel now refuses to render unless its page is the current one; the World Info UI suite went from intermittent to 18/18 three runs in a row.
- **Fixed, correctness:** `deleteWorldInfo` refuses books missing from ST's in-memory `world_names`, so deletion now refreshes that list first; the entry editor could crash on a book whose entry lacked `triggers` or held a non-string list, so the bridge now coerces list and text fields; a background drain called `renderPage()` and wiped unsaved typing on form pages; Trigger % clamped silently behind the field; Settings was unreachable (and with it the device-only reading preferences) whenever the engine was down; `AbortSignal.timeout` in the proxy probe could raise an unhandled rejection on older WebViews; folder moves could outrun the 60 s transport timeout; plus a dead World Info placeholder branch, a duplicate book fetch after creation, and a hardcoded version string in the Settings footer.
- **229 automated tests pass**, and the four browser suites pass against a real ST 1.19.0 fixture: World Info bridge 22, World Info UI 18 (+ slider-drag regression, stable across repeat runs), Settings 21 (+ focus regression), Home 10.
